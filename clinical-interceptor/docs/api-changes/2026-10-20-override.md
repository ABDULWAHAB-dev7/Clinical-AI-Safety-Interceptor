# API change: clinician override and FHIR REST source (Phase 3)

Approved by the project owner on 2026-10-20 (Phase 3 brief). API.md has no override flow, so this record is the contract
until API.md is amended.

## New endpoint: POST /v1/interceptor/override

Body (strict, extra fields refused):

| Field | Type | Notes |
|---|---|---|
| `report_id` | UUID | The audit report that holds the span |
| `span_id` | UUID | A span in that report, from `GET /v1/interceptor/audit/reports/{id}` |
| `override_reason` | string, 3 to 200 | Stored only as a SHA-256 hash |
| `attending_signature` | string, 3 to 200 | Self-asserted. Stored only as a pseudonym, `rev_` plus 16 hex |

Responses: 201 with `override_id`, `report_id`, `span_id`, `event_id`, `note_id`, `pipeline_status`, `reviewed_at`.
401 and 403 as elsewhere. 404 `REPORT_NOT_FOUND`. 400 for an invalid body. 409 `OVERRIDE_NOT_ALLOWED` when the span has
no warning or block, is not in the report, or was already reviewed.

Rules:
- Only a span whose finding is WARNING or CRITICAL can be overridden.
- Each finding can be overridden once. The review is appended, never edited.
- A BLOCKED note moves to `OVERRIDDEN_BY_CLINICIAN`. A note with only warnings keeps its status.
- The report itself is not changed. The original audit trace stays, so the history shows the block and the override.

## New scope: `interceptor:override`

Required by the override endpoint. Tokens without it get 403 `AUTH_SCOPE_INSUFFICIENT`.

## New error code: OVERRIDE_NOT_ALLOWED (409, clinical impact NONE)

## Schema change: pipeline status (migration 0002, db/schema.sql)

`intercepted_notes.pipeline_status` gains the value `OVERRIDDEN_BY_CLINICIAN`. The audit tables do not change. The
review is a row in `hallucination_reviews` (DATABASE.md section 4), which is already append-only.

## Identity and signature (limits)

The attending signature is a string the client supplies. Nothing verifies it. The reviewer reference is a pseudonym of
that string, and the client that submitted the override is recorded as a keyed hash of its certificate identity. A real
clinician sign-in (SMART launch, or an identity provider) is needed before an override can be called attributable.

## FHIR REST source (fhir/rest.py)

`fetch_everything(base, patient_id)` reads `GET {base}/Patient/{id}/$everything` over https, keeps the resource types the
verifier supports, reports anything dropped, and returns a `collection` bundle. The inline bundle path is unchanged.

Tested live on the public HAPI R4 server (`INTERCEPTOR_LIVE_FHIR=1`). That record has no facility MRN identifier, so the
verifier refuses it (fail closed), as intended. Only the first page is read.
